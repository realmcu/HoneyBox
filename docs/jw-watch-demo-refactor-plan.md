## 1. 背景与目标

现有 Android App 已有两套经过业务验证的页面结构：

- `wofit-android-base/.../WatchDataFragment.java`：同步、日期切换、历史摘要、分类数据详情和图表入口；
- `wofit-android-base/.../WatchDetailFragment.java`：设备信息和按设备能力动态显示的设置、提醒与控制项。

JW 协议在 App 侧对应 **UK 设备栈**（不是 MY/Veep 主路径）：

| App 对照 | 作用 |
| --- | --- |
| `deviceopt/v2/manager/uk/UKSDKManager.java` | JW（UkProtocol / `JWFunctionManager`）的 Android 封装入口 |
| `UKSettingsManager` / `UKFunctionManager` / `UKDataManager` | 设置、测量控制、历史同步的 UK 模块 |
| `UKHealthAndMonitoringActivity.java` | 「健康与监测」自动监测 UI；条目以 UK 能力为主，夹杂少量 MY/专项入口，Demo 只取 **UK 能对应到 JW SDK** 的部分 |

Demo 不复制完整 C 端 App 的账号、社交、上传和运营逻辑，而是把上述页面的交互骨架变成 SDK 的可验证入口。每个页面只能通过 `jw_watch_sdk` 的公开 API 工作，不可直接操作 BLE、帧通道、私有数据库或旧 JW session。

完成后的 Demo 同时承担四件事：

1. 为接入方提供可运行的 SDK 示例；
2. 为开发人员提供设备能力与设置覆盖检查页；
3. 为测试人员提供同步、历史数据与设置读写的验收入口；
4. 为协议排查提供操作结果、错误原因和必要诊断证据。

## 2. 最终导航结构

底部导航固定为四个 Tab：

| Tab | 页面职责 | 初始状态 |
| --- | --- | --- |
| 首页 | 引导、扫描与连接、初始化/认证、读取设备信息和能力集 | 始终可用 |
| 数据 | 健康历史同步、本地历史记录、分类详情和图表预留 | 会话就绪后可用 |
| 设置 | 基于连接设备实际能力的设置、提醒和控制验证 | 会话就绪后可用 |
| 功能 | 保留现有功能目录/API 调试入口，暂不重构业务结构 | 会话就绪后可用 |

移除现有“场景”和“设备”Tab。原“设备”中的连接和设备摘要职责迁到首页；原“场景”不保留独立入口。现有“功能”Tab 继续存在，用于展示未纳入设置页的 API 示例、测量与未来扩展能力。

### 2.1 Tab 解锁规则

不能只按 BLE `connected` 解锁。解锁条件必须是 SDK 会话 `ready`：连接已建立、必须的初始化/认证已完成、设备基础信息与能力集已得到有效结果。

```text
未连接 / 连接中 / 初始化中
  └─ 首页可操作；数据、设置、功能显示锁定状态

会话 ready
  └─ 读取到 device summary + feature/capability snapshot
      └─ 解锁数据、设置、功能
```

设备断开、认证失效或主动解绑后，立即收回后三个 Tab 的操作能力；已打开页面显示断连状态，不允许继续写入。首页保留重连与重新初始化入口。

### 2.2 首页的完成边界

首页不是简单的“连接按钮”，而是其余 Tab 的共同前置：

1. 扫描、选择设备、连接、断开与重连；
2. 显示连接阶段和可恢复错误；
3. 执行 SDK 规定的登录/绑定/初始化流程；
4. 获取并展示设备名称、MAC、型号、固件、电量等基础信息；
5. 获取并缓存本次会话的能力快照；
6. 明确展示是否已经满足 `ready`，以及未满足的原因。

首页读取的是 SDK 的 `device summary` 与能力 API；它不依赖服务端下发的设备配置。

## 3. 设置 Tab（第一优先级）

### 3.1 定位

设置 Tab 以 `WatchDetailFragment` 为 UI 与交互参考，可复用同仓库的图标、色彩和常见行项目样式，目标是做到视觉和使用习惯大致一致。实现不能直接搬运 Android Fragment 的业务依赖，而要由 Flutter 页面调用 SDK settings、control、device 和 notification 等公开服务。

该页的核心是“设备真实能力 + 操作验证”，不是 App 的运营配置页。因此：

- **唯一的显隐/可用依据**是当前连接设备的 SDK capability snapshot；
- 不读取服务器配置、AB 开关、账号角色、云端推荐或 App 私有偏好；
- SDK 实现未知与设备不支持必须区分，不能把未知静默当成不支持；
- 每一个写入项都应表达操作阶段：读取中、可编辑、提交中、成功、读回成功、仅已提交、失败；
- 页面断连时保留上次读到的值作为只读参考，并标注“设备已断开，可能已过期”。

### 3.2 能力判定与展示规则

设置项应有独立的 Demo metadata，至少包括：标题、图标、所属分组、所需 SDK feature、设备 capability 条件、读/写 API、是否支持读回、参数校验和资源依赖类型。

| 能力状态 | 行项目表现 | 用户可执行操作 |
| --- | --- | --- |
| SDK 已实现 + 设备支持 | 正常显示，展示当前值/摘要 | 读取、进入详情、修改或触发 |
| SDK 已实现 + 设备不支持 | 默认隐藏；诊断模式可显示为“设备不支持” | 不可写入 |
| SDK 尚未实现 | **普通模式也可显示一行**，标注「SDK 未支持」 | 不可写入；可链到功能 Tab 说明将来补齐 |
| 能力未知/读取失败 | 显示“能力待确认”与失败原因 | 重试读取，不可盲目写入 |
| 依赖资源服务（表盘/OTA 等） | 显示设备支持与「本轮不实现 / 资源未接入」 | 不可操作 |

原则：**先完成 Demo UI 与能力覆盖表**。现有 `jw_watch_sdk` / Demo 已覆盖大部分基础设置、测量与历史同步；缺口用「SDK 未支持」占位，不伪装成设备不支持或已验收。

普通使用默认隐藏「仅设备不支持」项；「SDK 未支持」建议在设置页保留可见占位（或诊断开关一键显示），便于对照 `WatchDetailFragment` / `UKHealthAndMonitoringActivity` 查漏。

### 3.3 写入与验证统一规则

所有设置统一遵守以下闭环，避免把发送成功误说成设备生效：

```text
读取当前值（如协议支持）
  → 用户修改并进行参数校验
  → 调用 SDK 写入 API
  → 等待业务回应
  → 可读回：重新读取并比对
  → 不可读回：显示“命令已提交，协议不支持读回确认”
```

对于结构体式配置（如勿扰、闹钟、提醒计划），必须先读完整配置再局部修改，避免覆盖用户未编辑的字段。同一种配置的写入串行；同步、测量或设备忙导致的拒绝，应在页面展示实际原因而不是只显示通用失败。

每次操作至少向用户展示：操作名称、开始/结束时间、成功或错误原因、是否已读回验证。更完整的请求/回调日志可跳转到功能 Tab 或诊断面板，不在设置页堆叠协议原始数据。

### 3.4 设置页面分组与首批范围

以下是页面信息架构；具体条目只在 SDK 已实现且设备支持时进入可操作状态。

| 分组 | 首批条目 | 验收方式 |
| --- | --- | --- |
| 设备概览 | 设备名、MAC、型号、固件、电量、能力摘要 | 重新读取设备信息，与首页一致 |
| 基础设置 | 同步时间、语言、12/24 小时制、单位制、用户资料、运动目标 | 写后读回；对时等不可读回项明确仅提交 |
| 显示与佩戴 | 屏幕显示、亮屏/亮度、翻腕亮屏、表盘/自定义 UI、隐藏健康功能 | 设置值读回或设备实际行为验证 |
| 提醒 | 消息提醒、闹钟、久坐、喝水、服药、事件提醒、勿扰 | 新增/修改/删除及读回；复杂计划保留完整字段 |
| 健康与监测 | 对齐 `UKHealthAndMonitoringActivity`：自动心率/血氧/血压/体温/压力等；女性健康、专项校准等按 SDK 覆盖表接入 | 能力判断、读写与重连后重新读取；MY-only 项不纳入 JW Demo |
| 设备控制 | 找设备、拍照控制、倒计时、电话功能、耳机、开关控制 | 触发成功与设备实际行为/回调 |
| 设备内容 | 电子卡、地址簿、SOS、天气/音乐等设备端内容 | SDK 支持时按相应读写/事件验收 |
| 安全与维护 | 设备密码、恢复出厂、固件信息 | 高风险操作单独确认；**OTA 入口本轮仅占位** |

**P1 首批**：设备概览 + 基础设置（对时、语言、时制、单位制、用户资料/目标若 SDK 已有）+ 能力判定与「SDK 未支持」占位行。提醒/控制/完整监测列表进 P2，但 metadata 可在 P1 先挂上标题与状态。

### 3.5 资源型与服务端型功能边界（本轮明确不做）

以下条目 **本轮不实现业务**，设置页最多显示「设备支持，本轮不实现」：

- **OTA**（包发现/下载/升级流程）；
- **表盘**（市场、自定义 UI 传输）；
- 字体下载、需云端内容的卡片/浏览器/运营入口。

设备固件版本等只读信息仍可在「设备概览」展示。

### 3.6 与 Android `WatchDetailFragment` 的对应关系

`WatchDetailFragment` 是视觉与功能清单参考，而非可直接复用的实现。其连接管理、`DeviceDataManager`、全局单例、App 数据库、网络检查、活动跳转和多厂商兼容逻辑不迁入 Demo。新页面通过单一的 SDK controller/session 注入，并将 Android 中的 `DeviceFunction` 判断映射为 SDK capability snapshot。

## 4. 数据 Tab（第二优先级）

> **已确认（2026-11-06）**
> 1. 数据首页 **catalog 全量展示**（含设备不支持项，用 chip 标注）；功能列表只控制可用态，不控制是否出现。
> 2. 类型详情 **默认进入今天**；支持左右切天 / 选日，交互对齐 App 现有数据详情。
> 3. 本阶段 **UI 先行**：顶部轻量同步条 + 卡片墙（查库最近一条）+ 详情壳（当日列表）；图表后补。

### 4.1 定位与最小闭环

数据 Tab 参考 `WatchDataFragment` 的信息层级：同步入口 → 类型卡片摘要 → 某类型某日详情。它负责展示 SDK 的历史同步和本地查询能力，不包含 App 的分享、社交关怀、徽章、健康平台上传或云端业务。

第一阶段先建立稳定骨架，图表详情只预留数据模型与路由，不要求立刻实现。

```text
数据 Tab 首页
  → 顶部轻量同步（开始 / 进度 / 最近结果）
  → 下方类型卡片全量展示（最近一条来自本地 DB）
  → 点击类型进入详情（默认今天，可切天）
  → 详情先展示当日记录列表；图表后续补齐
```

### 4.2 页面组成

| 区域 | 第一阶段内容 | 后续增强 |
| --- | --- | --- |
| 顶部同步条 | 开始同步、进行中进度、成功/失败摘要 | 分类型重试、重置同步标记（深链到现有 sync flow） |
| 类型卡片墙 | catalog 全量；摘要=最近一条；设备不支持仍展示 | 按能力隐藏开关（诊断模式） |
| 类型详情 | 默认今天；左右切天；当日记录列表 / 空态 | 日/周图表、区间统计、与 App 对照校验 |
| 历史诊断 | 现有 `JWHistorySyncFlowPage` 可作调试深链保留 | — |

类型展示必须同时考虑 SDK 是否实现、设备是否支持、当前本地是否有记录。没有记录不等于设备不支持；同步失败也不等于历史为空。

### 4.3 图表预留原则

图表不在设置页首期范围内，但数据模型应从一开始保留统一的时间序列接口：时间戳、数值/多指标、单位、记录质量和来源批次。图表层只能读取本地公开查询结果，不应自行解析协议帧或绕过数据库。

首个图表建议优先实现心率或步数日趋势，再逐步补血压、血氧、睡眠和其他多字段类型。图表必须明确时区、日期边界、单位与缺失值处理，才能用于与 Android App 或设备数据对照。

## 5. 功能 Tab 的保留策略

功能 Tab 保留现有目录和 API 样例结构，暂不以设置页重构为由删除。其职责是：

- 容纳实时测量、运动、通知、专项控制等不适合放入设置页的能力；
- 展示尚未产品化的 SDK API 和调用样例；
- 作为设置页“SDK 未实现/开发中”项目的可追溯调试入口；
- 后续承载更完整的诊断工具，但不得与正常 session 竞争 BLE 连接或启动并行同步。

## 6. 实施顺序与验收节点

> **当前冲刺范围：P0 → P1。** P2+ 排期延后；P3/P4 数据 Tab 可沿用现有 history/measure 页面做薄封装，不必等设置全部做完再动数据壳。

### P0：导航与会话门禁

1. 将底栏改为“首页 / 数据 / 设置 / 功能”；
2. 删除“场景”和旧“设备”Tab 的路由（连接与设备摘要并入首页）；
3. 将连接、初始化、设备摘要和能力读取集中到首页；
4. 以 `ready + capability snapshot` 驱动后三个 Tab 的可用状态；
5. 断连、初始化失败、重新连接时验证门禁和页面状态恢复；
6. 现有设置/历史/测量页可从「功能」或新 Tab 深链复用，避免 P0 重写业务。

**验收**：未就绪时不能误操作数据/设置；就绪后四 Tab 使用同一 session，且不产生第二条 BLE 连接。

### P1：设置 Tab 骨架与基础项

1. 建立设置 metadata（含 UK/`WatchDetail` 对照 id）、分组页面、通用读取/写入/结果组件；
2. 接入设备概览、对时、语言、时制、单位制等 **SDK 已有** 基础项（对接现有 `jw_settings_pages` / session API）；
3. 接入能力判定；**SDK 未支持** 行可见占位；表盘/OTA 行固定「本轮不实现」；
4. 「健康与监测」分组：对照 `UKHealthAndMonitoringActivity` 列条目，已有 `JWMeasure` 自动监测 API 的先接上，其余标 SDK 未支持；
5. 完成写后读回与“仅提交”提示的统一语义。

**验收**：支持项能读取、写入、按协议读回；设备不支持 / SDK 未支持 / 本轮不做（表盘·OTA）/ 未知 四类状态可区分；页面不要求新 SDK 能力即可合入。

### P2：设置 Tab 的提醒与控制

1. 逐项接入闹钟、勿扰、久坐、消息/事件提醒；
2. 接入找设备、拍照、倒计时等常用控制；
3. 将女性健康、电子卡、地址簿、SOS 等按 SDK 覆盖表持续补齐；
4. 为高风险操作增加确认和断连/设备忙处理。

**验收**：每个已声明支持的项都有明确操作入口、错误表现和真机验收步骤。

### P3：数据 Tab 首页与详情壳（UI 先行，当前执行）

1. 建立 `jw_data_catalog`（类型、图标、所需 function、查询入口）；
2. 数据 Tab 改为：顶部轻量同步条 + 全量类型卡片（查库最近一条）；
3. 类型详情默认今天，支持切天；当日记录列表 / 空态；
4. 设备不支持项仍展示并标注；无数据与不支持区分开。

**验收**：ready 后数据 Tab 可见全量卡片；同步后卡片摘要刷新；点进详情默认今天且可切天。

## 7. 不在本轮范围内

- 复刻 C 端 App 的登录体系、好友/关怀、分享、勋章、健康平台上传和运营内容；
- 绕过 SDK 直接使用 BLE、协议帧、旧 session 或 Android App 的数据库；
- 在没有资源服务的前提下实现线上 OTA、在线表盘市场、在线字体下载；
- 为了展示完整性而将尚未实现的 SDK 能力伪装成设备不支持或已验证。

## 8. 完成标准

Demo 改造完成不以“页面画出来”为准，而以以下事实为准：

- 首页能够在真机上稳定完成连接、初始化、设备信息与能力读取；
- 三个受保护 Tab 在会话状态变化时正确解锁和收回；
- 设置 Tab 的每个可操作条目都有能力依据、操作结果和正确的读回语义；
