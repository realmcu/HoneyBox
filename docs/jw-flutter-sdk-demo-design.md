# T4：JW Flutter SDK 与 Demo 产品设计

> 状态：设计基线。本文定义 T4 的公开 SDK、Demo、HoneyBox 装配、文档和自动化边界；实施分批、协议与数据库细节见 [JW SDK 实施计划](jw-watch-sdk-implementation-plan.md)，公共底层迁移见 [手表工程迁移计划](ws-watch-migration-plan.md)。
>
> 命名约定：Flutter 对外只提供 **JW SDK**，不暴露 V1/V2 字样。这里的“新设计”吸收 Android V2 的分层思路，但以 Android V1 的量产行为和真机证据为功能基线。

## 1. 目标与非目标

T4 交付的不是内部协议测试页，也不只是将旧 Flutter 目录搬进 package。它应同时满足三类使用者：

| 使用者 | 要完成的事 | 产品要求 |
| --- | --- | --- |
| SDK 接入开发者 | 了解可用能力、参数、前置条件与异步结果，并把调用放入自己的 App | Demo 是交互式集成参考，公开页面只调用公开 SDK API |
| HoneyBox 研发与测试 | 真机联调、定位会话/业务/协议问题、执行回归 | 有可选 Debug Console、稳定日志与自动化入口，不能污染对外主路径 |
| 后续 Android 重构 | 复用已经验证的 API 分组、模型语义、功能边界和验收证据 | Flutter 的公开契约、能力矩阵和示例可作为迁移参考，避免重新设计 |

完整交付包括：

- 独立 `jw_watch_sdk`，覆盖 JW 连接、身份、设备能力、设置、同步与存储、实时测量、运动、控制、通知和主动事件。
- 可从 HoneyBox 启动、也可在未来独立运行的 `jw_watch_demo`；它是面向接入方的演示工程，而非仅内部工具。
- 每项公开能力都有可追溯的 API、文档、Demo 操作、自动化 ID 与验证记录。
- 量产设备支持的能力以真机验证收口；SDK 未实现、当前设备不支持、会话未就绪三种状态必须区分。

不属于本 SDK/Demo 主线：OTA 升级实现、手机通知采集服务、七牛/文件上传、多设备原始采集。这些可使用相同 BLE 协调能力并在 HoneyBox 中组合，但不能成为 JW SDK 的隐式依赖。

## 2. 版本基线与对照原则

Android 代码存在 V1 与 V2 两套历史入口，不能机械地任选其一移植：

| 资产 | 在 T4 中的角色 |
| --- | --- |
| Android V1 | 量产协议行为、真实功能覆盖和固件兼容性的主要基线 |
| Android V2 | API 分组、Demo 信息架构和模型命名的重要设计参考；每项仍需验证其与 V1/真机是否等价 |
| Flutter JW SDK | 唯一的 Flutter 公开 API；采用 Dart 风格的 Future、Stream 和值对象，不复制 Android 单例/回调形态 |
| V1/V2 Android Demo | 功能目录、参数和交互参考，不是 Flutter UI 的逐页翻版 |

Flutter 不维护 `JwV1`、`JwV2` 两套平行接口。对外 API 冻结前，逐项维护能力矩阵；任何“已支持”的结论都要分别记录实现、设备支持和验证证据。

```text
Android V1 量产行为 ─┐
Android V2 设计参考 ─┼─> JW 能力矩阵 ─> Flutter JW SDK 契约
真机/固件实际行为 ──┘                         ├─> Demo
                                                ├─> 文档
                                                └─> 自动化与验收记录
```

每项能力至少包含：Android V1/V2 对照入口、协议/数据条件、Flutter API、参数和事件语义、实现状态、设备支持状态、单测/向量、Demo 路由、文档锚点、自动化 ID、型号/固件真机证据和已知差异。设备不支持不能替代 SDK 实现；Android 有接口也不能替代真机证据。

## 3. 不变的公共底层

T1–T3 已经提供 JW 与 WS 共用的可靠字节链路。T4 只在其上实现 JW 的 L2、业务会话、模型和数据库，不重建另一套 ACK、seq、重传或 BLE 队列。

```text
jw_watch_sdk（JW L2 / 会话 / 业务 / 模型 / 数据库）
                       ↓
          watch_frame_channel（T3，共用 L0/L1）
                       ↓
                watch_transport（T1）
              ↙                    ↘
 watch_transport_ble（T2）   watch_transport_simulation（T1）
```

约束如下：

- `watch_transport` 只负责连接、字节收发和连接生命周期；它不认识 JW 命令、业务回应或健康数据。
- `watch_frame_channel` 只负责当前共有 L0/L1 帧头、组包、分片、CRC、ACK、seq、重传和整帧发送顺序；它不解析 JW L2。
- `jw_watch_sdk` 负责 JW 请求/回应匹配、登录/绑定、能力判断、业务状态机、数据解析、存储和对外错误语义。
- 默认使用 BLE transport；高级接入和测试可注入连接工厂/运行环境。simulation 是测试与模拟设备的连接实现，不应让公开 JW API 依赖 WS 模拟行为。
- OTA 等独立工作流可参与 BLE 设备占用协调，但不强制经过日常 JW 帧会话。

## 4. 包边界与 HoneyBox 装配

```text
packages/
  jw_watch_sdk/                 公开 SDK；无 HoneyBox、页面或 Demo 依赖
  jw_watch_demo/                对外 Demo feature；只通过 jw_watch_sdk 使用 JW
  watch_lab_ui/                 通用展示组件，不直接控制 JW 连接或协议
  jw_watch_debug_console/       可选内部 feature；诊断、trace、Raw、脚本
  watch_transport*/             T1/T2
  watch_frame_channel/          T3

HoneyBox
  Watch Lab Hub → JW SDK Demo +（仅内部装配）JW Debug Console
```

### 4.1 `jw_watch_sdk`

- 可单独发布/以 path 依赖使用；不 import HoneyBox provider、路由、页面、Demo 资源或 WS SDK。
- 公开 API 不泄露 FlutterBluePlus、裸 GATT、帧序号或 HoneyBox 状态类型。
- 拥有 JW 专属公开模型、错误、身份和 `jw_watch.db`；不复用 WS 健康模型或表。
- 将“命令已提交”“帧已 ACK”“业务回应已收到”“读回已验证”明确表达为不同结果，不能把任意一个写成“设备已生效”。

### 4.2 `jw_watch_demo`

- 面向普通 SDK 接入者，所有普通功能页面只调用 `jw_watch_sdk` 的公开 API。
- 不直接创建 `WatchBleConnection`、写裸字节、解析帧或读写 SDK 私有数据库。
- 首期作为 HoneyBox 的全屏 feature 运行；以后添加很薄的 `example/` App 即可独立分发，不迁移或复制 UI。
- 代码按业务领域组织，路由、文档与自动化均以稳定 feature ID 关联。

### 4.3 `watch_lab_ui`

只提供可复用视图，而不是混合 JW 协议实现：会话状态条、功能目录、能力/状态标签、参数表单、操作结果、事件时间线、日志列表和空状态。JW 业务适配、会话所有权和页面路由留在 `jw_watch_demo`。

### 4.4 `jw_watch_debug_console`

只在 HoneyBox 或显式启用的开发构建装配。它可读取 SDK 暴露的受控诊断事件、会话摘要和 trace，并在没有业务会话或经会话独占许可时提供 Raw 操作。它不能与正常业务并发争抢同一个字节链路；外部 Demo 默认不显示也不依赖它。

## 5. JW SDK 公开设计

以下是分组边界，不锁定最终类名。T4.0 依据能力矩阵冻结具体签名。

```dart
final watch = JWWatch.create(config: config);

await watch.initialize();
watch.scan(...);
await watch.connect(target, identity: identity);

watch.session;       // 连接、身份、ready、能力与设备摘要
watch.device;        // 设备信息、电量、功能/固件
watch.settings;      // 用户、时间、语言、单位、显示、闹钟、提醒、开关
watch.measurements;  // 手动/实时/自动测量及结果流
watch.history;       // 同步、批次、离线健康记录查询
watch.sport;         // 设备端运动控制和实时事件
watch.controls;      // 拍照、找设备、音乐、天气、定制等
watch.notifications; // 来电、消息、设备端通知事件
watch.diagnostics;   // 受控观测，不要求普通接入方使用
```

### 5.1 会话与生命周期

连接不是 ready。公开状态至少区分：未初始化、扫描、连接中、字节链路已连接、登录/绑定中、ready、断开中、已断开、失败。SDK 拥有从扫描、选设备、连接、服务/通知准备、身份、登录/绑定、设备信息和能力读取到 ready 的完整流程。

- 身份稳定持久化；身份文件不存在/读写异常不得静默换一个身份以抢绑设备。
- 绑定、解绑和设备端确认是明确的业务流程；未认证连接可读哪些信息必须由协议和设备行为决定。
- 连接取消、超时、蓝牙关闭、意外断开、重连和旧代次迟到回应均清理本次会话任务。
- 同一设备的多个 SDK 实例受 transport/BLE 协调限制；不同设备的会话可按底层能力并行。

### 5.2 Future、Stream 与结果语义

- 操作以 `Future<OperationResult>` 或等价的明确结果完成；不能只以无错误返回伪装设备执行成功。
- 连接变化、主动上报、测量数据、同步进度和设备事件以 Stream 发布，并定义订阅释放、断连结束和重复订阅语义。
- 错误按初始化、权限、扫描、连接、认证、能力、参数、传输、超时、协议、存储和设备拒绝等阶段分类，并说明是否可重试。
- 能力状态、会话状态和 SDK 实现状态不能混为一个 bool；`unknown` 不静默视为支持或不支持。

### 5.3 业务覆盖

以下全部是 T4 覆盖范围。具体型号是否支持由能力和真机结果决定，不因某台设备缺少功能而省略 SDK 实现。

| 域 | 包含内容 |
| --- | --- |
| 开始使用、设备与身份 | 初始化、权限提示所需状态、扫描/过滤、连接/断开、登录/绑定/解绑、设备信息、固件、电量、能力、身份和重连策略 |
| 用户与设备设置 | 用户资料、时间/手机系统、目标、语言、时制、单位、日期、显示、亮度、亮屏、主页、设备开关 |
| 提醒与配置 | 闹钟、久坐、勿扰、高心率/热应激、饮水/服药、自动测量、睡眠/低氧及有效型号专属配置 |
| 健康测量与实时事件 | 心率、血压、血氧、体温、ECG、血糖、尿酸/血脂、体脂、体检、压力、紫外、Pulse、Sauna、HRV RMSSD 等有效公开能力 |
| 同步、存储与查询 | 历史同步、进度/取消/恢复、步数/睡眠/各类健康记录、去重、离线查询与删除；不兼容或迁移旧 journal |
| 通知与控制 | 来电/消息/接听/拒接、拍照、找手机/设备、音乐、计时、天气、女性健康、通讯录/SOS、定制通知/UI/样式颜色 |
| 运动 | 支持运动类型、状态查询、开始/暂停/恢复/结束、实时运动数据与状态变化 |

## 6. 面向接入方的 Demo

### 6.1 产品定位

`JW SDK Demo` 是交互式集成参考：开发者可以在手机上操作功能、理解支持条件和结果，再下载 Demo 工程查看完整实现。它不是把所有 API 平铺出来的协议控制台，也不是用教程遮挡功能操作的演示幻灯片。

默认对外首页使用业务语言；内部名称 Watch Lab 只用于 HoneyBox 入口和开发调试语境。

### 6.2 信息架构

```text
JW SDK Demo
├─ 开始使用与连接
├─ 设备信息与能力
├─ 用户与设备设置
├─ 健康测量与实时数据
├─ 数据同步与健康记录
├─ 通知、提醒与手机交互
├─ 设备控制、定制与表盘
├─ 运动与专项健康能力
├─ 当前设备与事件
└─ 开发者工具（仅显式开启）
```

所有页面共用一个 JW 会话。顶部常驻“设备会话条”：设备名/标识、连接阶段、登录状态、固件、能力加载状态与断开入口。功能页不能自行扫描、再建一条 BLE 连接或保存自己的登录状态。

首页按状态切换重点：

| 状态 | 首页重点 |
| --- | --- |
| 未连接 | 最短接入流程、权限/蓝牙状态、扫描和“首次连接”场景 |
| 连接/登录中 | 当前步骤、可取消操作、明确失败原因和恢复动作 |
| ready | 当前设备摘要、已支持能力、最近事件、常用操作、业务功能目录 |

### 6.3 功能页模板

功能广度通过少量稳定页面模板承载，而不是为每个 API 制作风格各异的孤立页面：

| 模板 | 用途 |
| --- | --- |
| 读取/写入配置 | 读取当前值、编辑参数、写入、回读校验；适用于设置和开关 |
| 单次/连续测量 | 开始/停止、实时状态、结果与异常；适用于心率、血压、血氧、体温等 |
| 同步与查询 | 同步进度、批次、入库结果、日期/范围查询和记录详情 |
| 列表编辑 | 闹钟、通讯录、SOS、提醒、通知开关等可编辑集合 |
| 控制与主动事件 | 拍照、音乐、天气、设备运动、通知事件和实时事件 |
| 特殊流程 | OTA 入口、解绑、表盘资源等带风险或多步骤流程；实际业务仍由独立模块负责 |

每项操作页固定呈现：用途说明、前置条件、能力状态、参数、执行控件、请求状态、设备结果/事件、错误说明。设置项在协议支持时提供“读 → 改 → 写 → 回读”的闭环；只支持发送的命令明确显示“已提交”而非“已验证”。

### 6.4 对外可见性规则

对外版本仅列出已交付的公开 SDK 能力：

| 情形 | 处理 |
| --- | --- |
| SDK 已交付，当前设备支持 | 显示并可执行 |
| SDK 已交付，设备不支持 | 显示为不可用，说明能力/固件原因 |
| SDK 已交付，会话未 ready | 显示前置条件和引导，不伪装为设备不支持 |
| SDK 未交付或仅内部实验 | 对外隐藏；内部覆盖率页记录计划和缺口 |

这保证对外 Demo 是 SDK 能力承诺，而不是旧 Android 目录或开发计划的投影。

### 6.5 代码与文档是次级信息层

手机上的第一优先级始终是功能操作和结果。“API 用法与源码”置于功能页底部的折叠区或二级动作，不占据主操作区。展开后提供：

- 最小、可复制的 Flutter 调用片段；
- 参数、回调/Stream 和释放说明；
- 对应开发文档锚点；
- 固定发布 tag 的 Demo 完整实现文件链接。

HoneyBox 的开发构建可额外提供“在工作区打开源文件”。外部版本不依赖这个能力；接入方下载 Demo 工程即可查看完整实现，也便于使用 AI 进行仓库级阅读。

## 7. 文档、源码与能力注册表

SDK API 与契约测试是真实行为来源；能力注册表是把 API、Demo、文档和自动化关联起来的产品索引，不能重新定义或复制 SDK 的参数类型。

```text
公开 API + 契约/协议测试
              ↓
能力注册表（路由、前置条件、文档、示例、自动化）
       ↙             ↓             ↘
    Demo UI       开发文档       自动化/验收
```

每项能力以稳定 ID 描述，例如 `measurements.heart_rate.single`。注册项至少包含：

```dart
FeatureSpec(
  id: 'measurements.heart_rate.single',
  title: '心率测量',
  requires: [SessionReady(), DeviceCapability.heartRate],
  publicApi: 'JWMeasurements.startHeartRate',
  docsAnchor: 'manual-measure/heart-rate',
  demoRoute: '/measurements/heart-rate',
  automationId: 'jw.measurements.heart_rate.single',
)
```

具体 API 名称以上例为准则而非承诺。参数控件应引用 SDK 的公开值对象、校验器和枚举；示例代码可手工维护以保持可读性，但必须在 CI 或 review 中校验其对应的 API 与路由仍存在。

建议 Demo 仓库拥有可读的领域结构：

```text
jw_watch_demo/
  lib/features/{connection,device,settings,measurements,history,
                notifications,controls,sport}/
  lib/feature_catalog.dart
  docs/{quick-start.md,scenarios/,feature-matrix.md}
```

`feature_catalog.dart`（或等价机器可读清单）提供 ID 到 Demo 源码、文档和自动化的映射。这样人和 AI 都不需要从页面标题猜测代码位置。

## 8. 场景示例

功能中心回答“SDK 有什么”；场景示例回答“我的应用应怎样接入”。首批场景应随 SDK 能力逐项真实交付：

1. **首次接入设备**：初始化 → 权限/蓝牙 → 扫描 → 连接 → 登录或绑定 → 获取设备信息与能力。
2. **发起健康测量**：判断能力 → 开始 → 订阅结果/状态 → 停止或处理异常。
3. **同步并查询健康记录**：开始同步 → 显示进度/批次 → 本地查询 → 说明部分成功、取消与重试。
4. **读取并修改设备设置**：读当前值 → 编辑 → 写入 → 回读验证。
5. **处理设备主动事件**：拍照、音乐控制、来电接听/挂断或运动状态等事件订阅与释放。

场景页可逐步引导，但不能接管功能页或阻碍直接操作；用户可随时退出场景进入对应功能。

## 9. AI 与自动化可控性

自动化是公开 Demo 的质量属性，不是额外的机器人 UI。每个可见操作应有稳定语义而非依赖坐标、图标或 Toast 文案：

- 页面、按钮、输入、结果和错误状态拥有稳定的 Flutter `Key`/语义 ID，使用 feature ID 派生。
- 请求统一暴露 `idle / running / succeeded / failed / unsupported / blocked` 等可断言状态；错误包含机器可读分类与人类可读解释。
- 设备结果与主动事件写入会话事件时间线，关联操作 ID；普通界面可读，自动化可结构化读取/导出。
- 支持稳定深链到功能或场景，如 `jw-demo://feature/measurements/heart-rate`；深链仍须执行会话前置检查。
- 自动化报告记录 SDK/Demo 版本、设备匿名标识、型号/固件、输入参数、操作/事件时间线、结果、错误与受控 trace 引用；避免记录身份和敏感健康原始数据。
- 内部调试模式可导出完整诊断包；外部版本只提供脱敏、用户明确触发的错误报告。

UI 自动化验证“公开用户路径”；协议向量、模拟器和真机脚本继续验证底层行为。三者互补，不能以任一种替代其他证据。

## 10. 开发者工具与普通 Demo 的隔离

开发者工具从右上角或构建配置显式进入，不混入八个对外业务目录。它包含：

- 会话状态机、请求队列和操作/事件时间线；
- 受控 L1/L2 摘要、帧关联与脱敏日志；
- transport/frame 冒烟与 Raw 命令；
- 自动化场景执行、故障复现和诊断包导出。

Raw 发送只允许在无业务会话、会话暂停且取得独占权、或专门诊断连接中执行。正常 SDK Demo 的同一连接由 `jw_watch_sdk` 会话独占；诊断工具不能绕开 session 与业务并发写入。

## 11. T4 交付节奏与验收

现有实施阶段保持 T4.0–T4.7；本文补充各阶段的 SDK/Demo 产品收口标准。

| 阶段 | SDK 重点 | Demo/文档增量 |
| --- | --- | --- |
| T4.0 | 全量能力矩阵、公开 API 与模型边界 | 冻结信息架构、feature ID、页面模板和文档索引 |
| T4.1 | 扫描、连接、身份、ready、设备/能力 | 首次接入场景、会话条、设备与能力页；只经公开 SDK 调用 |
| T4.2 | 设置、显示、提醒、配置 | 读取/写入/回读模板与设置功能页 |
| T4.3/T4.4 | JW 数据库、历史同步、离线查询 | 同步进度、批次、查询、记录详情与数据场景 |
| T4.5 | 测量、控制、通知、运动、扩展能力 | 测量/实时事件、控制、通知、运动及专项页面 |
| T4.6 | 对外 Demo、独立 example、CI | 源码/文档链接、场景完整化、自动化语义和外部工程验证 |
| T4.7 | 真机全量回归与宿主切换 | 覆盖率报告、型号/固件证据、已知限制和发布材料 |

每个能力完成的最低闭环：公开 API 与参数/错误语义、协议/单元测试、必要的数据库映射、Demo 操作入口、文档锚点、自动化 ID，以及相应型号/固件的真机结果。没有设备的能力可完成实现和向量验证，但必须标记“未取得真机证据”，不能用“当前设备不支持”宣布全量验收。

## 12. 最终验收

T4 完成时应能证明：

1. 新 SDK 从 JW L2 到 BLE 真实通过 T1–T3 公共链路，没有旧 JW 会话或私有 ACK/重传旁路。
2. JW 与 WS 可独立或同时接入，公开模型、会话、身份与数据库彼此隔离。
3. 对外 Demo 能独立安装；接入者无需理解 GATT、frame channel 或 HoneyBox 即可完成常见业务集成。
4. HoneyBox 使用同一 Demo feature 运行，并可选装调试工具，不维护第二套功能 UI。
5. 全量能力矩阵对 Android V1、Android V2、Flutter API、Demo、文档、自动化和真机证据可追溯；未实现、未支持和未验证项分别公开记录。
6. Demo 工程、能力目录和 feature ID 足以让开发者或 AI 快速定位“某项能力的 API、页面、文档、源码和验收用例”。
